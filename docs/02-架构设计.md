# 02 · 架构设计

> 阶段 3 交付物之一。

## 1. 分层架构

```
前端 SPA（原生 HTML/CSS/JS，无构建步骤）
  仪表盘 / 个人配置 / 搜索设置 / 岗位列表 / 岗位详情 /
  待投递审核 / 招呼语 / 投递记录 / HR 回复 / 简历生成 / 任务日志
        |
        | HTTP + JSON (REST)
        v
API 层       app/server.py        路由 / 校验 / 错误约定 / 静态资源
        |
服务层
  profile_service   档案与设置（含敏感字段脱敏）
  job_service       岗位池：筛选 / 排序 / 去重 / 状态
  score_service     六维评分（规则引擎 + AI 融合）
  greeting_service  招呼语生成与版本管理
  resume_service    简历解析 / 事实库 / 定制简历生成与导出
  apply_service     投递确认、执行、记录
  track_service     回复同步（IMAP / 手动）、通知
        |
任务层       app/tasks.py
  任务表 + 调度线程 + 状态机 + 限流 + 可中断 + 进度上报 + 结构化日志
        |
AI 层        app/ai/
  provider 抽象（openai_compatible / rules / mock）
  + prompt 契约 + 事实约束校验 + 结果缓存 + 成本统计
        |
采集层       workers/*.cjs（Node + Playwright，驱动本机 Chrome）
  或 app/collectors/*.py（官方 API / 公开列表页，stdlib urllib）
        |
数据层       SQLite（data/qiuzhao.db）+ 文件仓（resumes/、exports/）
```

**为什么采集层放 Node**：Playwright 已存在于本机 Codex 运行时（`playwright@1.62.1`），而 Python 侧没装 playwright、也没有网络权限去 `pip install`。用 Node 做浏览器自动化、Python 做业务与数据，是这台机器上**零安装**的唯一解。两者通过 JSON（stdout）通信，边界干净；Node 侧只负责"打开页面 → 抽取 → 输出 JSON"，所有判断逻辑都在 Python。

## 2. 技术选型与实测依据

| 层 | 选型 | 实测依据 |
| --- | --- | --- |
| 后端 | Python 3.12 标准库 http.server + sqlite3 | 运行时自带，已跑通 |
| 前端 | 原生 HTML/CSS/JS，无构建步骤 | 已跑通并截图核对 |
| 数据库 | SQLite（WAL） | sqlite 3.53.1 |
| 文档解析 | pypdf / python-docx / openpyxl / pandas | 运行时已装 |
| PDF 生成 | reportlab（新建）+ Word COM（DOCX 转 PDF） | reportlab 已装；Word.Application COM 已注册、WINWORD.EXE 存在 |
| 浏览器自动化 | Node 24 + playwright 1.62.1，channel=chrome | 模块已装；沙箱内启动被拦，需在本机验证 |
| AI 调用 | OpenAI 兼容 HTTP（stdlib urllib），无 key 降级规则引擎 | 运行时没有 requests / httpx / openai |
| 任务调度 | 自研轻量任务表 + 后台线程 | 无需 Redis / Celery |

**未选 FastAPI 的理由**：本机 Python 是 Codex 运行时自带的，没有独立 venv，也没有网络权限装 fastapi / uvicorn / pydantic-settings。引入它们要么破坏运行时一致性，要么需要先装正式 Python 并联网建 venv。等 MVP 稳定、你决定长期维护时，可以把 API 层平滑换成 FastAPI——服务层已经解耦。

## 3. AI 层设计（含"禁止编造"的落地机制）

### 3.1 Provider 抽象

```
class LLMProvider(Protocol):
    name: str
    def complete(system, user, json_schema=None, timeout=60) -> dict
```

实现两个：`OpenAICompatibleProvider`（DeepSeek / 通义 / Kimi / OpenAI 通用）、`RulesProvider`（无 key 时降级，保证流程不中断）。

配置全部来自环境变量，代码内零硬编码：

```
QIUZHAO_LLM_PROVIDER=openai_compatible | rules
QIUZHAO_LLM_BASE_URL=https://api.deepseek.com/v1
QIUZHAO_LLM_MODEL=deepseek-chat
QIUZHAO_LLM_API_KEY=***
QIUZHAO_LLM_TIMEOUT=60
```

### 3.2 事实约束（防幻觉的关键设计）

简历解析后落成**结构化事实库** `resume_facts`，每条事实有唯一 `fact_id`：

```
F12  教育  某高校 环境设计 本科 2025.09-至今
F23  服役  部队 义务兵 2023.03-2025.03
F31  技能  SketchUp 熟练
```

所有 AI 生成文本（匹配理由、技能差距、招呼语、定制简历段落）都要求返回结构化 JSON，每句话带 `fact_ids`：

```json
{ "text": "我在部队服役两年，适应高强度工作节奏", "fact_ids": ["F23"] }
```

校验规则：**任何 `fact_ids` 为空或指向不存在事实的句子，一律标记为"待人工确认"，并在导出时阻断**。这条把"禁止编造"从口号变成代码级约束。

### 3.3 六维评分（需求第四章）

| 维度 | 数据来源 | 默认权重 |
| --- | --- | --- |
| 技能匹配 | 岗位 JD 关键词 与 档案技能/事实库 的交集 | 30 |
| 学历匹配 | 岗位学历要求 vs 本科在读 | 15 |
| 地点匹配 | 城市优先级（东营 > 济南 > 其他意向 > 非意向） | 20 |
| 经验匹配 | 岗位经验要求 vs 服役 + 校园经历 | 10 |
| 薪资匹配 | 岗位薪资区间 vs 期望区间 | 10 |
| 职业方向 | 岗位族 vs 求职意向（"专业不限"额外加权） | 15 |

权重可在设置页调整；每个维度必须输出**得分依据**（命中了哪些词、差在哪），并允许对单条岗位人工覆写分数。

## 4. 任务系统

```
queued --> running --> (paused <--> running) --> done
                    \-> failed   （带错误堆栈）
                    \-> stopped  （用户主动停止）
```

- 调度：单后台线程轮询 `tasks` 表，按 `priority, next_run_at` 取任务；同一来源串行执行，避免触发风控。
- 限流：每任务可配 `rate_limit_per_min`，采集器强制遵守，默认 6 次/分钟。
- 可暂停：任务循环在检查点读 `paused / cancel_requested`，能在单个请求粒度内停下。
- 日志：每次运行写 `task_logs`（level / module / message / payload），前端"任务日志"页实时轮询。
- 重启恢复：进程重启后把 `running` 任务标记为 `interrupted`，可手动续跑。

## 5. 授权与合规模型

需求反复强调"用户明确授权"，落成一张 `authorizations` 表：

| scope | 说明 |
| --- | --- |
| `collect:<source>` | 授权采集某个来源 |
| `ai:analyze` | 授权把岗位 JD 发给 AI 提供方 |
| `ai:resume` | 授权把简历事实发给 AI 提供方 |
| `apply:confirm` | 每次投递前的一次性确认（不长期有效） |
| `track:imap` | 授权读取你的邮箱 |

每个自动化动作执行前检查对应 scope，未授权则拒绝并提示在前端授权；授权可撤销，撤销后相关任务自动停止。前端在触发 AI 调用前展示"将发送哪些字段"。
