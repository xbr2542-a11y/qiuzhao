# 01 · 需求分析与可行性

> 阶段 1 交付物。结论先给：**整体可行，但有三块需要改写需求边界**（自动打招呼、HR 回复抓取、账号体系）。

## 1. 目标用户画像（脱敏）

本工具不是为"泛泛的求职者"设计的，而是围绕一类具体画像做的取舍。以下为脱敏后的
关键事实，姓名、学校、服役单位等可识别信息已移除：

| 维度 | 内容 |
| --- | --- |
| 学历路径 | 专升本：专科（艺术设计类）→ 本科（设计类）在读 |
| 毕业时间 | 2027 年（本科在读），即 **2027 届** |
| 特殊资产 | 两年义务兵服役经历（退役军人身份） |
| 技能 | Word/Excel/PPT、CAD、SketchUp、V-Ray、Photoshop、AI 工具 |
| 求职意向 | 数据分析 / ToB 半导体销售及半导体相关行业 / 外贸 / 采购供应链 |
| 意向城市 | 山东（东营、济南）优先，其次北京、深圳、广州、成都 |

这四条对设计有直接影响：

1. **跨专业求职**：主修环境设计，意向却是数据分析 / 半导体销售 / 外贸。因此"专业档位"过滤（不限 / 相关 / 明确限定）是一等公民，且必须输出"为什么被过滤"的可解释理由。
2. **退役军人**：这是央国企、国企、事业单位招聘中的**定向加分项**（部分岗位设"退役大学生士兵"专项计划）。渠道库必须能识别这类专项岗位，而不是当成普通岗位混在一起。
3. **简历是表格化 DOCX**：简历用 7 张表格承载教育/服役/社团/荣誉/技能。纯文本抽取会丢结构，解析器必须**按表格单元格逐格提取并做角色归类**，不能只抽段落文本。
4. **本地已有 Word 2016**：定制简历的 DOCX→PDF 转换可以直接走 Word COM，不必额外装 LibreOffice，也不必用在线转换服务。

## 3. 逐模块可行性判定

| 模块 | 判定 | 依据与边界 |
| --- | --- | --- |
| 用户配置中心 | 可行 | 纯本地表单 + SQLite |
| 岗位搜索中心 | 可行 | 本地条件筛选，无外部依赖 |
| 岗位采集中心 | 部分可行 | 只抓**公开可访问**的招聘列表页与官方开放接口；登录墙后、需短信验证、有验证码的页面**不做**——这是需求自己定的红线，我完全同意并会落实为代码级约束 |
| AI 岗位筛选 | 可行 | 需要 LLM API key；无 key 时降级为规则引擎（技能词命中/学历/城市/薪资区间），保证不依赖外网也能跑 |
| 投递确认中心 | 可行 | 批量选择 + 二次确认 + 执行记录，全部本地 |
| HR 招呼语生成 | **需改写边界** | 生成文本完全可行；**自动发送不可行也不做**——BOSS 直聘这类平台的"打招呼"是平台内行为，自动发送属于绕过平台限制，与需求第三章自己定的规则冲突。落地方式：生成 → 一键复制 → 你在已登录的浏览器里发送；可选"半自动填入输入框，你点发送" |
| 投递记录 | 可行 | 状态机 + 时间线 |
| HR 回复跟踪 | **需改写边界** | 三种合法来源：① 你自己邮箱的 IMAP 只读同步（需授权）；② 手动粘贴；③ 面板内手动标记。**不做**模拟登录招聘平台抓站内消息 |
| 定制化简历 | 可行 | python-docx 生成 DOCX，Word COM 转 PDF，本机已具备 |
| 任务管理 | 可行 | SQLite 任务表 + 后台调度线程，支持启动/暂停/恢复/停止 + 限流 + 日志，**不需要 Redis/Celery** |
| 身份认证 | **建议砍掉** | 单人本机工具引入注册/登录/JWT 只增加攻击面和维护成本。改为：只监听 `127.0.0.1`，可选访问令牌用于局域网（默认关闭） |

## 4. 必须由你确认的三个决策点

### 决策 A：AI 提供方
需求要求 AI 分析，但没有 key 时我能给的只有规则引擎（能跑，但"技能差距/风险提示/招呼语"会退化成模板拼接）。

默认方案：**Provider 抽象层**，支持 OpenAI 兼容协议（DeepSeek / 通义 / Kimi / OpenAI 只换 `base_url` 和 `model`），无 key 时自动降级为 `rules` provider。密钥只从环境变量读（`QIUZHAO_LLM_API_KEY`），不硬编码、不入库。

**需要你做的**：告诉我用哪家、把 key 配进环境变量。在此之前我先实现 `rules` provider，保证流程能跑通。

### 决策 B：招呼语的"发送"环节
我按需求第三章的合规红线处理：**程序生成、你发送**。如果你要"程序填入输入框、你点发送"，明确告诉我即可——那需要在你已登录的浏览器里操作，属于半自动范畴（与上一轮确认的投递口径一致），我可以做，但不会做全自动发送。

### 决策 C：技术栈
见 `02-架构设计.md`。默认走**零第三方依赖**路线（Python 标准库）：代价是没有 FastAPI 的自动接口文档，好处是当前环境立刻能跑、将来打包 exe 时体积和坑都小得多。

## 5. 风险清单

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 渠道页面改版 | 采集器失效 | 每个渠道一个适配器 + 失败日志 + 失效告警；解析失败不静默，标记"需人工确认" |
| AI 幻觉编造经历 | 投递翻车、面试对不上 | **事实约束机制**：AI 每句话必须能追溯到结构化事实库条目，无来源的句子标红并阻断导出（见 02 文档） |
| 简历与个人信息泄露 | 隐私事故 | 全部本地存储；调用 AI 前展示"将发送哪些字段"，默认只发脱敏后的 JD + 技能清单，不发手机号/身份证 |
| 平台风控 | 账号被封 | 不做登录墙后的自动化、不做验证码识别、限制请求频率、自动化动作需显式授权 |
| 采集量不足 | 工具没用 | 先保证"官方渠道 + 手工粘贴导入"两条路都能进库，采集器是增量而非唯一入口 |
